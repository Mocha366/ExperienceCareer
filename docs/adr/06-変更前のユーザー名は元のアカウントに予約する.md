# 変更前のユーザー名は元のアカウントに予約する

## 決定

変更前のユーザー名は、使っていたアカウントに予約する。ADR-03 の「変更後、旧名が使われていなければ再利用できる」は、この決定で置き換える。

Username が公開 URL 用でユニークであること、使える文字が小文字英字と数字のみであること、現在の Username の公開ページは Account を経由せず Username から Profile を引くことは、ADR-03 のまま。

- ユーザー名を変更したら、変更前の名前をそのアカウントに予約する。変更のたびに、手放した名前が予約に加わる。取得した名前は、古いものから手放さない。
- 他人は、予約された名前を新規登録でも変更でも取得できない。
- 本人は、自分が予約している旧名に戻せる。戻した名前は、その時点の現在のユーザー名になる。戻すときに手放した名前は、あらためて予約する。
- 新しいユーザー名の取得は、初回のあと3回までとする。1つのアカウントが押さえられる名前は、初回と合わせて最大4つである。
- ストックを消費するのは、まだ自分が持っていない新しい名前を取得するときだけである。自分が予約している旧名へ戻す操作は、ストックを消費しない。
- ストックを使い切ったあとは、新しい名前は取得できない。予約済みの名前のあいだの移動はできる。
- リダイレクトを実装するまでは、旧 URL は 404 である。リダイレクトしない。
- リダイレクトは後で実装する。予約された旧 URL は、そのアカウントの現在のユーザー名の公開プロフィールへ繋ぐ。本人がその旧名に戻しているあいだは、その名前は現在のユーザー名であり、リダイレクト元にしない。
- ユーザー名を変更する前に確認を出す。初回のユーザー名設定では出さない。リダイレクトを実装するまでは、確認は過去の URL が開けなくなることを示す。

未決のままにする。

- 予約をどのテーブルに、どの列で持つか。
- リダイレクトの繋ぎ方。HTTP のステータス、API と画面のどちらで移すかは決めていない。
- リダイレクトを実装したあとの確認文。
- 確認をどの UI で出すか。

## 切った案

- 空いていれば誰でも旧名を再利用できる（ADR-03 の一文）
- 本人も旧名を使えなくする
- リダイレクトはせず、旧 URL は開かないままにする
- 変更前の確認を出さない
- 予約を直近3件だけ残し、それより古い名前は他人が取得できるようにする
- 自分の旧名へ戻す操作も、変更回数に含める

## 理由

- 旧 URL を他人が取得すると、ES に残ったリンクから別人の経歴が見える。1つの URL で本人のイベントキャリアを伝える価値が壊れる。
- 他人が取れないうえに本人も使えないと、その名前は誰も使えない死に ID になる。本人は自分の旧名に戻せる。
- リダイレクトを入れるまでは、旧 URL は開けない。変更してから気づくと、ES に載せたリンクが切れたままになる。変更前の確認で、過去の URL が開けなくなることを示す。
- リダイレクトは後から足す。それまでは 404 のままにする。
- 予約を直近3件だけにすると、4回目の変更でいちばん古い名前が他人に渡る。ESに残るのは、たいていちばん最初のユーザー名である。
- ストックなら、使った名前はすべて予約されたままになる。1人が押さえられる数は、初回と3回までで頭打ちになる。
- 自分の旧名へ戻しても、他人が使える名前は減らない。この操作まで回数に含めると、ストックを使い切ったあと、予約済みの名前を現在のユーザー名に戻せなくなる。
