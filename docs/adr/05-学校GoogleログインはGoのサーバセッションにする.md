# 学校 Google ログインは Go のサーバセッションにする

## 決定

学校ドメイン（`@gn.iwasaki.ac.jp`）の Google ログインを、次の方針で実装する。

### セッションの持ち方

サーバセッション + HttpOnly Cookie にする。

- Go がセッション ID を発行し、サーバ側（メモリや DB）に `セッション ID → ユーザ情報` を持つ
- ブラウザの Cookie にはセッション ID だけを載せる（誰か・メールなどの中身は載せない）
- 認証の正はすべて Go。フロントはログイン画面と編集 UI に集中する
- ログアウトはサーバ側のセッション記録を消して、その ID を無効にする

### OAuth の受け口

認可 URL の発行と Google からのコールバック受信は、どちらも Go が行う。

- セッション発行と同じ場所（バックエンド）で管理する
- Client Secret など秘密はフロントに出さない

### ライブラリ

次の組み合わせを使う。

- `golang.org/x/oauth2` … 認可 URL 発行・authorization code → token 交換
- `github.com/coreos/go-oidc/v3` … Google の ID トークン検証（`sub` / email / 必要なら `hd`）

具体的なセッション保存先（メモリか DB か）やテーブル設計は、この ADR では決めない。実装 issue で進める。

### ドメイン制限

メール（または Google の `hd`）が `@gn.iwasaki.ac.jp` のものだけログインを許可する。それ以外は拒否する。

### ローカル開発とコールバック URL

- Google Cloud の OAuth クライアントを使う
- Client ID / Client Secret は `.env` に置き、リポジトリにコミットしない
- MVP（ローカル実装）のコールバック URL は `http://localhost:8080/...` 想定とする
- デプロイ・本番以降の URL は、そのタイミングで変更する

プロフィール編集・経験登録の API 設計、Account テーブルの詳細、フロントのログイン UI の見た目は、この ADR では決めない。

## 切った案

### セッション

- JWT をフロントが保持する方式（Bearer）

### OAuth の受け口

- フロント主導（BFF なし）で Google とやりとりする方式

### ライブラリ

- 標準ライブラリ中心 + Google の token 検証を自分で組み立てる
- `golang.org/x/oauth2` だけ（ID トークン検証を自前または userinfo 依存にする）
- Goth（`markbates/goth` など）のような多プロバイダ枠
- Next.js の Server Actions で認証する（このリポは Vite SPA + Go。ADR 02）

### その他

- パスワード自前管理（この ADR の選択肢としては採用しない。学校 Google を前提にする）

## 理由

### なぜサーバセッションか（なぜ JWT ではないか）

- 現状の規模では扱いやすさがサーバセッションの方が嬉しい
- Cookie には ID だけなので、中身がブラウザに出てこない
- ログアウト時にサーバの記録を消せば、その ID は無効になる
- フロントはログイン画面と編集 UI に集中でき、認証の正を全部 Go に寄せられる（境目がきれい）
- JWT は正しくやれば同程度にできるが、localStorage 保管や無効化の難しさなど、ミスしやすい落とし穴が多い

### なぜ OAuth の受け口を Go にするか

- セッション発行と一緒にバックエンドで管理したい
- フロントが Google とやりとりする寄りになると、秘密の置き場や境目がわかりにくくなる

### なぜ専用ライブラリ（上記の2つ）か

- OAuth / OIDC の細部を全部見えても、自分でセキュアに実装し切れる保証がない
- まずは専用ライブラリで実装し、依存が増えることは今回は仕方ないとして割り切る
- `x/oauth2` + `go-oidc` は Go で Google ログインする定番で、フローと本人確認が分かれており、学校ドメイン判定に載せやすい
- `x/oauth2` 単体だと ID トークン検証が薄くなり、自前の穴を避けたい意図と逆行しやすい
- Goth などは今回 Google（学校アカウント）だけなので過剰

### ドメイン制限・ローカル URL

- 対象は `@gn.iwasaki.ac.jp` の学生だけ（design doc）
- MVP はローカル実装が先。本番 URL はデプロイ時に変えればよい
