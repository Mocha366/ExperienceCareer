# Overview (概要)

##　ASHIATO

技術力評価会の資料とフィードバックを**人単位**でつなぎ、「特定の人が半期ごとにどう評価され、どこでグレードが上がったのか」という一本のストーリーとして辿れるサービス。ロールやドメインなどの属性から人を探し、その人の評価会履歴（以下 HH）を時系列で読める状態をつくる。

## What we provide (何をつくるのか)

提供するものは **「人を探す」→「その人の評価会履歴を読む」** のシンプルなビューアである。

1. **人の検索** — バイネーム（名前）で直接引くか、属性で絞り込んで人の一覧を得る。属性は「評価者 / 被評価者」「ロール(役割、リーダー、メンバー)」「ドメイン」「プロジェクトフェーズ」。評価者しばり（特定の評価者が担当した人だけに絞る）もできる。
2. **評価会履歴（HH）の閲覧** — 検索結果から人を選ぶと、その人の履歴が新しい順に並ぶ。1 行は「実施回（例: 26-1st）」「そのときのグレード（例: E2）」「提出資料のリンク」「フィードバックのリンク」で構成される。半期をまたいで並ぶことで、**E1 → E2 に上がったのがいつで、その前後で何を書いていたのか**が 1 画面で分かる。

価値としては「GitHub に散っている半期ごとの資料を、人という軸で読み直せるようにする」こと。新しくデータを作るのではなく、既にあるデータの見え方を変える。

## BackGround (バックグラウンド)

技術力評価会の資料とフィードバックは既に **GitHub 上に HH（評価会履歴）として存在している**。しかしそれは**半期単位でまとまっている**ため、「26-1st の全員分」「25-2nd の全員分」という切り口でしか読めない。

その結果、**特定の人が半期をまたいでどう変化したか**、とりわけ **グレードが上がったタイミングがどこだったのかが分からない**。知りたいのは「この人がどこで E1 から E2 になり、そのとき何を出したのか」という一本のストーリーなのに、データの並び方がそれを許していない。

これは情報が無いのではなく、**情報の軸が違う**という問題である。半期ごとに置かれているものを人ごとに読み替えるには、閲覧者が各半期のディレクトリを一つずつ遡り、目当ての人の資料を手で拾い集める必要がある。この手間のせいで、実際にはほとんど誰も遡らない。

## User Story (ユーザーストーリー)

**同じロール・同じフェーズのプロジェクトに立つエンジニア** は、本サービスにより、ロール・ドメイン・フェーズで人を絞り込んで HH を読め、自分と近い状況の実例を自分のプロジェクトマネジメントの参考にすることができる。

**次のグレードを目指しているエンジニア** は、E1 から E2 に上がりたいと考えているとき、実際に上がった人が何を出したのかを参考にしたいという動機を持つ。本サービスにより、グレードが上がった回の資料とその前後の履歴をまとめて読め、「何が足りていて何が足りないのか」を具体的な資料ベースで判断できる。

**新卒・若手のエンジニア** は、これから数年のキャリアを設計しようとしているとき、先輩がどういう順序で何を積み上げてきたのかを知りたいという動機を持つ。本サービスにより、特定の人の半期ごとの歩みを一本の流れとして読め、自分のキャリアの見通しを持てる。

## Alternatives Considered (検討した代替案)

Overview で述べたゴールは「半期ごとに散っている評価会の記録を、**人という軸**で一本のストーリーとして読めるようにする」ことである。したがって代替案は実装の手間ではなく、**そのゴールをどこまで満たせるか**で比べる。比較軸は次の 3 つとした。

- **人軸で辿れるか** — 半期をまたいで一人のストーリーが読めるか
- **グレード変化点に到達できるか** — 「上がった回の資料と FB」まで辿り着けるか
- **鮮度が保たれるか** — 半期ごとの更新に人手なしで追従するか

| 案                                             | 人軸で辿れるか                                                                               | グレード変化点に到達できるか                                                                   | 鮮度が保たれるか                                                                 |
| ---------------------------------------------- | -------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| **人軸で HH を引けるビューアを作る（採用案）** | ○ 一人の履歴が新しい順に一覧で並ぶ。半期をまたいだ流れがそのまま画面になる                   | ○ グレードが変わった回が一覧の中で見え、その行から資料と FB に直接飛べる                       | ○ GitHub の HH を参照するため、半期ごとの追加がそのまま反映される                |
| GitHub の HH をそのまま見る（現状）            | × 半期単位で並んでいるため、一人分を読むには閲覧者が各半期を自分で横断して組み立てるしかない | △ 資料と FB は一次情報として揃っているが、どの回で上がったのかを示す並びがないので到達できない | ○ 一次情報そのものなので常に最新                                                 |
| 評価委員がスプレッドシートにまとめる           | ○ 人ごとの行として並べられる                                                                 | △ リンクを貼れば辿れるが、何を残すかが転記者の判断に依存し、資料・FB まで揃う保証がない        | × 半期ごとの人手更新が前提で、更新が止まった時点で読める範囲が古いまま固定される |
| AI に聞けるようにする                          | △ 「この人の履歴は」と問えば答えは返るが、一覧として並んだ状態が残らない                     | △ 変化点を挙げさせることはできるが、根拠が実際の資料と一致している保証がない                   | △ データソースを繋げば追従するが、答えの内容が更新に追いつくかは検証しづらい     |
| 詳しい人に直接聞く                             | △ 人軸の語りは得られるが、聞ける相手がいるかに依存し、誰でも同じ情報に届くわけではない       | △ 「あの人はあの回で上がった」は聞けても、そのときの資料と FB には辿り着けない                 | △ 語り手の記憶の範囲に限られ、対象の広さと確かさが安定しない                     |
| Slack でグレード履歴を見る                     | △ グレード変更のアナウンスは人単位で流れるが、資料・FB と結びついていない                    | × グレードが変わった事実までで、その回に何を出したのかには辿り着けない                         | ○ アナウンスは半期ごとに流れ続ける                                               |

3 軸すべてを満たすのは採用案のみである。現状（GitHub 直読み）と Slack は**人軸と変化点**が欠け、スプレッドシートは**鮮度**が欠ける。AI と直接ヒアリングは答えを得られはするが、**同じ問いに同じ資料で辿り着ける状態**にはならない。採用案は既にある HH の見え方を人軸に変えるだけで 3 軸を同時に満たすため、これを選んだ。

## Functional Requirements（機能要件：MVP）

MVP は **「属性で人を探す」** と **「その人の HH を時系列で読む」** の 2 つに絞る。データ入力の仕組みは作らず、既存の GitHub 上の HH を参照する。

### Must

| #      | 機能                         | 何を・誰が・どうなるか                                                                                                                                              |
| ------ | ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| F-1    | バイネーム検索               | **利用者が**、バイネーム（名前）を入力して人を特定できる。完全一致でなくても部分一致で候補が出る                                                                    |
| F-3    | 検索結果の一覧表示           | **システムが**、条件に合致した人を一覧で返す。一覧には名前と現在のグレードを表示し、そこから履歴画面へ遷移できる                                                    |
| F-4    | 評価会履歴（HH）の時系列表示 | **利用者が**、選んだ人の履歴を新しい順に閲覧できる。1 行は「実施回（26-1st など）」「そのときのグレード（E1 / E2 など）」「資料へのリンク」「フィードバック」を含む |
| F-5    | 既存 HH データの取り込み     | **システムが**、GitHub 上の半期単位の評価会データを読み取り、人を軸に並べ替えて保持する。取り込み対象は資料・FB・実施回                                             |
| >F-4.5 | グレード履歴                 | グレードの変化履歴を保持する                                                                                                                                        |

### Should

| #   | 機能                 | 何を・誰が・どうなるか                                                                                                                |
| --- | -------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| F-6 | グレード変化点の強調 | **システムが**、履歴のうちグレードが上がった回を視覚的に強調する。「どこで上がったのか」を一覧のまま把握できる                        |
| F-7 | 評価者しばり         | **利用者が**、「特定の評価者が担当した人」に絞って検索できる                                                                          |
| F-8 | 属性による絞り込み   | **利用者が**、「評価者 / 被評価者」「ロール」「ドメイン」「0→1 / 1→∞ のフェーズ」を条件に人を絞り込める。条件は組み合わせて指定できる |

### Could

| #   | 機能             | 何を・誰が・どうなるか                                                                 |
| --- | ---------------- | -------------------------------------------------------------------------------------- |
| F-8 | 履歴の横並び比較 | **利用者が**、複数人の HH を並べて比較できる。同じロールの人同士で歩みの違いを見られる |
| F-9 | 公開範囲の制御   | **被評価者が**、自分の HH を誰まで公開するかを設定できる                               |

> ※ F-9 の公開範囲制御は画像に記載なし。評価会の資料と FB は個人の評価情報であり、全社公開を前提にするなら合意形成が必要になるため、論点として明示する目的で補完。
